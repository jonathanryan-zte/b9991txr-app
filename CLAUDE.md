# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-page web app for logging truck expenses for one vehicle (B 9991 TXR, Hino Dutro 2013) directly into a Google Sheet ("History B 9991 TXR"). Built for a non-technical Indonesian-speaking fleet operator, used mobile-first on an iPhone. There is no build step, no framework, and no package.json — the entire frontend is one HTML file.

- `index.html` — the whole app: inline `<style>` + inline `<script>`, no bundler.
- `apps-script.gs` — Google Apps Script source, deployed as a Web App bound to the Google Sheet. This is the only backend.
- `manifest.json`, `sw.js`, `icon-192.png`, `icon-512.png`, `icon-512-maskable.png` — PWA install support (installable on iOS via "Add to Home Screen").

**Deployment is two separate steps with no CI:**
1. `index.html` (+ manifest/sw/icons) is hosted on GitHub Pages at `https://jonathanryan-zte.github.io/b9991txr-app/`, from `git@github.com:jonathanryan-zte/b9991txr-app.git` (branch `main`). This working directory is a clone of it and pushes over SSH, so deploying the frontend is just commit + push. Pages takes up to a minute to serve the new file — verify with `curl` against the live URL and grep for a symbol only the new version has, rather than assuming.
2. `apps-script.gs` goes into the Apps Script editor, then Deploy > Manage deployments > New version. The deployed Web App URL is hardcoded in `index.html` as `ENDPOINT` — changing Apps Script code alone does nothing until a new version is deployed there. The bound project is "API b9991pxr" (`script.google.com/home/projects/1wz6Qtf2JqYsIHxSDUVLEaBI-kfvCrwBAzhheAbfEciuaDU6KmXJxq13u/edit`). It can be driven through the Claude in Chrome extension using the user's own Google session; paste large code via the clipboard (`pbcopy` then Cmd+A/Cmd+V) because a hand-retyped paste has silently truncated before and produced `Unexpected end of input`. **Always confirm with the user before clicking Deploy** — it changes the live backend the truck operator depends on. To check the editor's content matches this repo without dumping source through the page, hash it in-page (`monaco.editor.getModels()[0].getValue()` + SHA-256) and compare; note the editor strips the file's trailing newline.

There are no tests, no linter, and no local dev server config. Verification is done by exercising the real functions in a browser against realistic inputs (paste actual OCR text into `parseSpr` rather than idealized samples — every OCR bug so far was invisible to clean test data), and by calling the deployed Apps Script URL with `curl`. Those `curl` calls to `script.google.com` are slow, often over a minute; run them in the background rather than assuming they hung.

## Architecture

### Frontend (`index.html`)

Single page with 4 tabs toggled by JS (`.tab` buttons / `.panel` divs, one `active` class each): **Perbaikan**, **Uang Jalan**, **Tagihan & Cicilan**, **Ringkasan**. Each of the first three is a `<form>` that POSTs to Apps Script via `sendToSheet()`; **Ringkasan** is read-only, fetching aggregated data instead.

Key pieces to know before changing anything:

- **`ENDPOINT`** (top of the `<script>` block) is the Apps Script Web App URL. All reads and writes go through it via `fetch`.
- **Apps Script POST responses come back through a redirect** (`script.google.com` → `script.googleusercontent.com`). Plain `fetch()` follows this transparently in real browsers — do not "fix" this by adding manual redirect-following logic; that was tried and breaks things (see git history / prior conversation) because `curl`-style manual redirect handling behaves differently than browser fetch.
- **Uang Jalan OCR scanning** (`runOcr`, `parseSpr`, `preprocessForOcr`): lets the user photograph a "Surat Perintah Ekspedisi" delivery slip and auto-fills Tanggal / No DO/SPE / Tujuan / Customer. Runs entirely client-side via Tesseract.js (loaded from CDN). `parseSpr(text)` is regex-driven against the *specific* layout of this one company's delivery slip (date + DO number + origin + destination + customer name all on one whitespace-separated line) — if the OCR text format ever changes, this is the function to revisit. **The data row is located by anchoring on the `Pandegla` token (`isPandeglaToken`), not by matching the leading date + D/O number** — on real dot-matrix scans those first two columns are frequently destroyed (one real capture read `22.08.2026 76788711 1708` as `Q t 11 1`), while the warehouse token survives. Everything after that token is destination city + customer. The old date-anchored regex is kept only as a fallback. Note `looksLikeGudangAsal` returns `true` for punctuation-only tokens (it's the loose stripper for that fallback path) — never use it as the anchor, use the strict `isPandeglaToken`. Both the Tujuan and Langganan label fallbacks explicitly skip the column-header line (`Gudang Asal / Tujuan / Langganan`), which OCR mangles into things like `& gl D \ sudang Asal Tujuan Lanaganan` and which previously leaked into the Tujuan field as `Lanaganan ||`. Other deliberate behaviors: (a) the origin warehouse is **never** read from OCR — it is the constant `GUDANG_ASAL` (`"TFJ Pandeglang"`), and only the destination city is parsed, because this truck always departs from the same warehouse; (b) the parsed city is fuzzy-matched (`levenshtein`/`bestKotaMatch`) against the destination cities already present in the Sheet's history (via `tujuanLookup`) so OCR typos like `TANGERAWG` snap back to `Tangerang`, and the city is always emitted in Title Case via `titleCase` (`TFJ Pandeglang - Cilegon`) because the user wants column D written that way — the Sheet's older rows are mixed-case, which is harmless since route lookup lowercases both sides — this means route autofill and city correction both degrade gracefully to raw OCR text if the `?action=lookup` fetch failed; (c) Tanggal prefers the document's **"Tgl Muat"** field and only falls back to the first date anywhere in the text (the D/O date, which can differ from the loading date); (d) the customer name is likewise snapped to an already-used spelling via `bestCustomerMatch` against the `customers` list returned by `?action=lookup`. That matcher is deliberately conservative — it refuses to correct when two known names are equally close (ambiguous) — so a genuinely new customer is never forced onto an old one. It also tries progressively shorter prefixes of the OCR name, longest first, because the slip prints depot/SO codes after the name (`AZRIEL,TK /SO M3 (CN`) while the Sheet records it as just `azriel`. Candidates are deduplicated by normalized form first: the Sheet holds the same name under several casings (`Alva Jaya Lestari` / `alva jaya lestari`), and without dedup they tie, trip the ambiguity guard, and silently disable correction for the most-used names. When it does correct, `parseSpr` records the raw OCR text in `result.customerAsli` and `applyScanResult` shows the before/after to the user; keep that visible, it's the only signal that a substitution happened. `preprocessForOcr` (grayscale → contrast stretch → block-adaptive threshold) only runs as a retry fallback when the first OCR pass finds fewer than 2 of the 4 fields, not always-on — it's slower and can hurt already-clean scans. If that still fails, `runOcr` re-runs OCR at 90°/270°/180° and keeps whichever reads most fields (sideways photos otherwise read as literally zero fields), updating `ujScanRotation` and both preview images through `setScanImage`. The data-row search starts **below** the column-header line and skips `salesman`/`stock point`/`branch` lines: the header area carries `Mr CNS - STOCK POINT PANDEGLANG (M3)`, whose `PANDEGLANG` token otherwise wins the anchor search and yields Tujuan `M3` with a date as the customer name.
- **The truck does not only run from TFJ Pandeglang.** The Sheet's route history also contains Mayora, Cikupa, Indofood Cibinong, KMG, CSS and other origins. The `GUDANG_ASAL` constant applies **only to the OCR scan path**, because the SPE slips being photographed are always TFJ Pandeglang dispatches. Never force that prefix onto hand-typed input: `normalisasiTujuanInput` only completes a bare city when history actually supports it (exact `TFJ Pandeglang - <city>` route, or exactly one historical route ending in that city), and otherwise leaves what the user typed alone. For the same reason `knownKotaList` returns `{utama, semua}` — city fuzzy-matching tries TFJ Pandeglang destinations first so a scan can't snap onto a city that only exists on some other origin's route.
- **Route-based autofill** (`applyTujuanLookup`, `findByKotaTujuan`): after a Tujuan is entered/scanned, looks up historical Uang Jalan amount for that exact route (normalized), falling back to a match by destination city alone if only one historical route ends in that city. It first runs `normalisasiTujuanInput()`, which expands a hand-typed bare city ("serang") into the full `TFJ Pandeglang - SERANG` form so manually-entered rows match the Sheet's existing formatting. Currently **only Uang Jalan autofills — Invoice was deliberately made manual-only** per explicit user request; don't reintroduce Invoice autofill without checking.
- **`Ringkasan` tab** (`loadRingkasan`/`renderRingkasan`) — the "Uang Jalan terakhir" list must render `r.uangJalan` (sheet column E), **not** `r.invoice` (column H); Invoice is routinely left blank in this Sheet, so binding that list to Invoice makes every row read Rp0. `buildSummary` returns both fields per row, so the two are easy to mix up. It lazy-loads on first tab click and also silently refreshes after every successful form submit (via `loadRingkasan()` call inside `wireForm`'s success path) — it's fetching `?action=summary` each time, so don't make this eager/on-page-load without reason.
- **Scan photo preview** (`scan-accordion`) is an inline accordion (CSS grid-template-rows animation) between the tab bar and the card content, not a modal/lightbox — this was a deliberate UX choice (a floating/draggable panel and a fullscreen lightbox were both tried and rejected) so the photo stays visible while the user scrolls to fill in fields below it.
- **No literal non-ASCII characters in JS strings set via `textContent`/`innerHTML` template literals** — e.g. use `&mdash;`/`&middot;` HTML entities in markup, or ASCII fallbacks (`"..."` not `"…"`) in JS strings. This bit us once: GitHub Pages/local servers without an explicit charset can mis-serve raw UTF-8 in dynamically-set text as mojibake. The `<meta charset="UTF-8">` at the top of `<head>` is required — don't remove it.
- **`<meta name="viewport">` in `<head>` is required** — without it iOS Safari renders the page at desktop width and zooms out, making everything tiny. Already fixed once; don't let it regress.

### Backend (`apps-script.gs`)

`doGet(e)` and `doPost(e)` are the only entry points (standard Apps Script Web App shape). Dispatch is by query param / body field, not by route:

- `doGet` — no `action` param returns a plain "API aktif" string (health check). `?action=lookup` returns `buildTujuanLookup()` — `{ tujuan, customers }`, where `tujuan` maps normalized route string → most-common Uang Jalan/Invoice (computed via mode, not average/last-row, to ignore blank rows and one-off outliers) and `customers` is the distinct customer names from column I sorted most-frequent-first, used by the frontend purely for OCR typo correction. `?action=summary` returns `buildSummary()` (recent rows + today/this-month totals + the live SELISIH formula value read straight from `PERBAIKAN!H1`, not recomputed).
- `doPost` — `body.sheet` selects `addPerbaikan` / `addUangJalan` / `addTagihanCicilan`, each of which appends one row to the matching Google Sheet tab and returns the new row number.

**The Google Sheet's column layout is load-bearing and not self-documenting from the script alone** — every `addX`/`buildX` function writes/reads specific `getRange(row, col, ...)` column indices that must match the sheet's actual columns:
- `PERBAIKAN`: A NO, B TANGGAL, C TINDAKAN, D HARGA, E BAYAR KE BRU, F (a `=D<row>` mirror formula, must be written for every new row), G KETERANGAN. H1 holds a live SELISIH formula — read it, never recompute it in Apps Script or JS.
- `UANG JALAN`: A NO, B TANGGAL, C NO DO/SPE, D TUJUAN, E UANG JALAN, F/G are unused legacy columns (skip them, do not write), H INVOICE, I CUSTOMER.
- `TAGIHAN DAN CICILAN`: A NO, B BULAN, C TAGIHAN, D CICILAN, E OPERASIONAL.

`nextNo(sheet, col, startRow)` computes the next auto-increment NO by scanning existing values (not `lastRow+1`), because rows are sometimes edited/reordered by hand in the Sheet.

`readTailRows`/`parseIndoDate` in `buildSummary`'s totals path parse dates stored as free-text strings like `"23 Agu 2026"` (written by the frontend's `fmtDateID`) — `Date.parse` does not reliably handle this format in the Apps Script V8 runtime, hence the manual Indonesian month-name lookup table. Keep the frontend's date-string format and this parser in sync if either changes.
